# Codex 트레이스 리더 · 제품 요구사항

초안 · 2026-11-23

[제품 철학](product-philosophy.md)

## 1. 목표와 첫 버전 범위

**사용자가 Codex가 수행한 작업을 전체 흐름에서 개별 행동과 기록 근거까지 따라가며 자유롭게 관찰할 수 있게 한다.** 특정 검증 내역을 확인하러 온 사용자와, 미리 정한 질문 없이 도구 사용이나 성공한 작업 과정을 둘러보는 사용자가 같은 화면에서 시작한다. 작업을 위임하는 사람과 개발 과정을 살펴보는 사람이 대상이며, Codex 내부 기록 형식에 익숙할 필요는 없다.

첫 버전은 Windows에서 **로컬 Codex 채팅 한 건**을 읽는다. 같은 채팅의 `rollout-*.jsonl` 파일과 `trace-*` 번들을 여러 개 등록할 수 있다. 대화는 선택한 rollout의 기록과 확인된 이전 구간을 표시하고, 상세 흐름은 선택한 번들 하나를 보여준다. 기록의 전체 흐름, 개별 행동, 원본 근거로 이어지는 읽기 경험을 검증한다. 정신모형이 달라지고 이후 위임에 적용되는지는 별도의 제품 가설이다.

백그라운드 감시, 실행 중 개입, 번들 간 이벤트 병합, 다중 세션 연결·분석, 자동 오류 탐지와 AI 진단, 프롬프트 추천과 스킬 최적화는 MVP 범위 밖이다. UI와 고정된 행동·메시지 유형명은 한국어로 표시하고, 자연어 메시지는 기록된 언어로 보여준다. 선택형 로컬 번역은 언어 장벽이 핵심 탐색을 막는지 확인한 후 검토한다.

## 2. 사용자 흐름

| 조작 | 화면 동작 |
| --- | --- |
| **최근 채팅 찾기** | 첫 화면에 이 PC의 Codex 채팅을 최근순으로 최대 100개 보여준다. 제목, 첫 요청과 날짜로 검색해 원하는 채팅을 바로 열 수 있다. 다른 위치의 기록은 파일 직접 열기로 선택한다. |
| **세션 기록과 첫 번들 열기** | 세션 파일과 첫 상세 트레이스 폴더를 입력하거나 선택한다. 같은 채팅으로 확인하면 채팅 ID, 세션 기록, 선택한 번들의 전체 흐름을 표시한다. 첫 화면에서 질문을 입력하거나 오류를 고르지 않고 바로 둘러볼 수 있다. |
| **세션 기록 보기 / 번들 선택** | 세션 기록 화면과 등록된 번들 하나의 상세 화면을 오간다. 상세 화면에는 선택한 번들, 시작 시점, 기록 상태와 마지막으로 확인된 범위를 표시한다. 각 보기가 다루는 범위를 구분할 수 있어야 한다. |
| **rollout 탐색·추가·선택** | 사용자가 찾기를 요청하면 등록한 위치에서 같은 채팅의 미등록 파일을 제안한다. Codex 표준 위치에서는 `sessions`의 날짜 폴더와 `archived_sessions`를 탐색한다. 사용자가 다른 위치의 파일을 직접 추가할 수도 있다. 화면 상단에서 볼 rollout을 선택한다. |
| **대화 턴과 상세 트레이스 간 이동** | 채팅과 턴 ID가 확인된 경우에 대화에서 상세 트레이스의 턴으로 이동한다. 해당 턴을 담은 번들이 여러 개면 선택지를 제시한다. 상세에서 대화 턴으로 돌아갈 때 출발한 화면의 읽던 위치를 복원한다. |
| **턴 펼치기 / 행동과 근거 보기** | 관심 있는 행동에서 실행 주체, 입력·결과, 앞뒤 행동, 확인된 관계와 기록 근거를 살핀다. 근거를 연 뒤 타임라인에서 읽던 위치로 돌아갈 수 있다. |
| **갱신** | 선택한 rollout, 이어서 읽는 등록된 이전 rollout, 선택한 번들을 다시 읽는다. 선택한 소스를 유지하며 같은 행동을 안정적으로 식별할 수 있으면 선택과 읽던 위치를 복원한다. |
| **상세 기록 찾기** | 채팅을 열 때 기본 검색 위치에서 소속이 확인된 번들을 등록한다. 사용자가 다시 찾거나 검색할 상위 폴더를 추가할 수 있다. 필요한 경우 번들을 작성한 실행 파일을 안내하고 사용자의 확인 뒤 변환한다. |
| **트레이스 폴더 직접 추가** | 경로를 이미 알거나 저장 위치가 다르면 폴더를 직접 선택한다. 같은 채팅으로 확인된 번들을 추가한다. |

`갱신`은 등록 경로만 다시 읽는다. 최근 채팅 목록을 처음 열거나 목록을 갱신할 때 Codex의 로컬 `sessions` 폴더를 확인한다. 추가 rollout은 사용자가 찾기를 요청했을 때 탐색한다. 트레이스 폴더는 채팅을 열거나 다시 찾기를 요청할 때 확인한다. 등록한 경로가 이동했거나 삭제됐으면 해당 경로와 이유를 표시하고, 세션 파일을 다시 지정하거나 번들 폴더를 직접 추가할 수 있게 한다.

상세 기록은 관찰하려는 세션 시작 또는 재개 전에 활성화돼 있어야 확보할 수 있다. 해당 시점의 번들을 제공할 수 없으면 세션 파일에서 읽을 수 있는 정보와 상세 기록이 필요한 항목을 구별해 보여준다. 식별 가능한 유효한 세션 파일은 세션 보기에서 열 수 있다. 번들이 없다는 사실만으로 기록 설정이나 작업 수행 여부를 단정하지 않는다. 첫 화면에는 지원하는 기록의 위치를 고르는 방법과 상세 기록을 미리 확보하는 방법을 안내한다. [Codex 상세 트레이스 구조와 기록 설정](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md)

## 3. 데이터 계약과 변환

| 소스 | 역할과 범위 |
| --- | --- |
| `rollout-*.jsonl` | 매니페스트에 대응하는 채팅 ID와 개별 rollout 파일의 ID를 확인한다. 선택한 파일에 `history_base`가 있으면 등록된 이전 파일에서 지정한 바이트·순번 경계까지 읽는다. 참조를 확인할 수 없으면 해당 구간이 빠졌음을 표시하고 확보한 기록을 보여준다. |
| `manifest.json` | `root_thread_id`와 세션 ID를 대조한다. 값이 일치할 때만 상세 번들을 연결하고, 미확인·불일치는 문제가 있는 소스와 함께 표시한다. `trace_id`로 중복을 방지하고, `started_at_unix_ms` 최신순으로 정렬한다. 같은 시각에는 `trace_id`로 순서를 고정한다. |
| `state.json` | 공식 reducer가 만든 파생 데이터다. 선택한 번들에 기록된 스레드와 턴, 모델 호출, 도구의 입력·결과와 연결 관계를 구조화하는 데 쓴다. |
| `trace.jsonl`과 `payloads/` | reducer의 입력이자 원시 근거다. 파일이나 페이로드 ID·참조를 사용해 표시된 항목과 원본의 관계를 확인한다. |

Codex는 재개하는 로컬 채팅의 세션 파일을 이어 쓸 수 있다. 상세 번들은 기록 실행 단위로 생성되므로 같은 루트 채팅에 여러 번들이 대응할 수 있다. 같은 채팅이라는 검증은 소속을 확인하며, 각 번들이 채팅의 동일한 시간·이벤트 범위를 덮는다는 보장은 별도로 확인해야 한다. [Codex 세션 재개 코드](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/thread_processor.rs) · [상세 트레이스 구조](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md)

되돌리기로 저장한 후속 rollout은 채팅 ID를 유지하면서 파일 ID가 달라질 수 있다. 복원된 대화의 각 항목은 실제 원본 rollout과 줄을 가리킨다. 상세 트레이스와 대화는 같은 루트 채팅에서 명시적으로 기록된 `turn_id`와 `codex_turn_id`가 일치할 때 턴 단위로 연결한다. [Codex의 기록 복원 코드](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/thread-store/src/local/rollout_lineage.rs#L65-L188)

1. **상세 트레이스 탐색.** `CODEX_ROLLOUT_TRACE_ROOT`, Windows의 로컬 `codex-rollout-traces`, 사용자가 추가한 검색 위치의 바로 아래에서 후보를 찾는다. 등록 경로는 건너뛰고 후보의 `manifest.json`으로 소속을 확인한다. 읽을 수 없는 매니페스트는 다음 탐색에서 다시 확인할 수 있다.
2. **선택한 번들 하나 변환.** 기록에 사용한 Codex 실행 파일로 `codex debug trace-reduce <번들 경로> --output <임시 경로>`를 실행한다. 먼저 데스크톱 스키마 3 번들을 지원 대상으로 검증한다. 같은 스키마 번호 또는 PATH에서 찾은 다른 설치본만으로 호환성을 판단하지 않는다. 사용할 실행 파일을 확인할 수 없거나 명령이 지원되지 않으면 변환을 중단하고 원인을 표시한다. [Codex reducer 설명](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md) · [Codex CLI 구현](https://github.com/openai/codex/blob/main/codex-rs/cli/src/main.rs)
3. **결과 반영.** 소스별로 읽기와 파싱에 성공한 스냅샷을 한 단위로 반영하고 확인 시점을 표시한다. 재읽기나 변환에 실패하면 그 소스의 이전 스냅샷과 확인 시점을 유지하고, 실패한 대상 경로와 이유를 표시한다. 첫 읽기부터 실패했다면 해당 소스의 새 결과가 없음을 표시한다. 선택한 번들의 데이터와 다른 번들의 이전 결과가 섞이거나, 이전 갱신 요청이 더 최신 선택을 덮어쓰지 않게 한다.
4. **부분 기록 처리.** 닫힘 이벤트가 없으면 `여기까지 기록됨`과 마지막으로 확인된 시점을 표시한다. 종료 여부나 현재 실행 상태는 기록이 뒷받침하는 범위에서만 표시한다. 읽을 수 있는 부분은 보여주고, 페이로드의 잘림·누락, 확인할 수 없는 연결, 재읽기 실패를 각각 알아볼 수 있게 한다.

## 4. 읽기 경험과 근거 표시

사용자는 다음 세 수준을 한 흐름에서 오갈 수 있어야 한다. 턴을 접어도 기록에 있는 요청 제목, 행동 수, 기록된 상태를 볼 수 있게 한다. 펼치면 루트와 관련 하위 에이전트의 행동, 선택한 항목의 앞뒤 맥락과 확인된 연결이 드러난다. 접기와 시각적 위계로 화면 밀도를 낮추고, 오류 여부나 시스템이 매긴 중요도에 따라 행동과 근거를 배제하지 않는다. 타임라인과 상세 패널을 나란히 두는 방식은 한 가지 구현안이며, 구체적인 배치와 스타일은 창 크기와 읽기 동선에 맞춰 정한다.

읽기 화면은 채팅 제목과 요청·진행 과정·답변을 먼저 보여준다. 질문 상단에서 진행 과정과 답변으로 바로 이동할 수 있다. 도구 이름과 대상은 확인된 도구명과 고정 인자에서 구성한다. 진행 항목의 시각과 대상·상태는 바로 확인할 수 있고, 상세의 실제 입력과 결과는 접어서 표시한다. 반환값의 유무, 최종 응답 유무, 기록된 종료 코드는 각 사실에 맞는 문구로 표시한다. 현재 화면이 대화 기록과 상세 실행 기록 중 어느 소스를 읽는지 표시한다. 내부 이벤트는 원본 기록 보기에서 열 수 있으며, 파일 경로와 ID는 기록 정보에서 확인한다.

| 읽기 수준 | 화면 요구사항 | 근거와 표시 규칙 |
| --- | --- | --- |
| **전체 흐름** | 요청과 응답, 턴별 행동, 기록된 상태를 훑는다. 행동 유형과 실행 주체를 구별하며, 오류가 없는 흐름도 같은 방식으로 펼친다. | 식별 가능한 기록의 턴 연결로 행동을 묶는다. 행동명·건수·요약은 기록된 유형과 고정 규칙에서 나온다. 기록에 없는 제목이나 진행률은 생성하지 않는다. |
| **개별 행동** | 누가 무엇을 요청했는지, 어떤 도구가 어떤 입력을 받았고 어느 결과를 반환했는지, 앞뒤로 어떤 행동이 있었는지 본다. 확인된 관계를 통해 관련 행동과 다른 실행 주체를 찾을 수 있다. | 호출·결과·요청·전달 관계는 기록 ID와 연결 필드로 확인한다. 동명 호출은 독립된 행동으로 유지한다. 관계가 불명확하면 확인된 주체와 필드만 표시한다. |
| **기록 근거** | 표시를 뒷받침하는 값을 보고 원본 위치를 찾는다. 화면이 붙인 한국어 이름이나 구조화한 관계는 어떤 필드와 규칙에서 나왔는지 확인할 수 있다. | 세션은 `rollout`의 레코드를, 상세는 같은 스냅샷의 `state.json` 객체와 필드를 가리킨다. 원시 레코드나 본문을 확인할 수 있으면 로컬에서 접근할 수 있게 하고, 참조만 있으면 파일 위치와 확보된 ID 또는 참조를 표시한다. |

- **순서와 인과.** 타임라인은 턴과 턴 내부 행동을 오래된 기록부터 표시한다. 시각이 같으면 기록된 순번을 우선하고, 순번도 없으면 안정적인 ID로 표시 순서만 고정한다. 실제 순서를 확인하기 어려운 경우 표시 순서의 한계를 드러낸다. 시간상 인접하거나 병렬로 보인다는 사실은 실행 관계나 원인을 입증하지 않는다. 이전 문맥에 포함된 메시지는 기록된 턴 연결에 따라 구분한다.
- **호출 종료와 실행 결과.** 호출 상태가 `completed`이고 명령의 종료 코드가 `1`이면 `호출 종료`와 `종료 코드 1`을 각각 표시한다. 코드의 의미는 도구의 관례와 기록된 출력에 근거해 해석할 수 있다.
- **반환 결과와 모델 입력.** 예를 들어 `model_visible_output_item_ids`에 있는 항목이 특정 모델 요청의 `request_item_ids`에서 확인될 때 해당 요청에 포함됐다고 표시한다. 시스템·개발자 지침, 모델의 도구 요청, 하위 에이전트의 작업 전달과 반환도 확인된 발신자·수신자·관계에 따라 표시한다. 반환값의 포함, 응답에서의 인용, 실제 산출물 반영은 각각 별도의 근거를 요구한다. 모델의 비공개 내부 추론과 행동의 원인은 화면이 추정하지 않는다. [도구 데이터 구조](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/src/model/runtime.rs) · [모델 요청 데이터 구조](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/src/model/conversation.rs)
- **원시 근거 접근.** 파생 필드, 원시 본문, 잘린 본문, 원시 참조만 확인 가능한 경우를 구별한다. 압축 샤드의 페이로드처럼 앱에서 직접 열기 어려운 경우 확보된 위치·ID와 제한을 알린다. 모든 payload를 복원하는 별도 디코더는 MVP 필수 조건에서 제외한다. 현재 디스크에 있는 원본이 이전 스냅샷과 일치하는지 확인할 수 없으면, 이전 화면의 근거로 단정하지 않는다. [Codex의 원시 근거와 파생 데이터 구분](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md)

### 대표 사용 사례

| 진입 상황 | 관찰 경로와 사용자가 형성할 수 있는 질문 |
| --- | --- |
| **사후 조사** | 완료 보고에서 테스트 범위가 궁금해 번들을 연다. 검증 턴에서 테스트 명령을 골라 대상, 종료 코드, 확보된 출력을 확인한다. 보고에서 말한 범위와 당시 확인 가능한 범위가 같은지 살피고, 후보 빌드의 동작을 별도로 확인할지 정한다. |
| **질문 없이 둘러보기** | 타임라인을 훑다가 `rg "authentication" src/`를 펼친다. 경로와 출력을 보고 어떤 범위가 검색됐으며 빈 결과로 어디까지 말할 수 있는지 스스로 묻는다. 다른 탐색 행동을 이어 보거나 그 지점에서 관찰을 끝낼 수 있다. |
| **성공한 개발 과정 보기** | 성공 사례에서 수용 기준 확인, 기대 동작을 고정한 테스트, 구현, 재검증, 문서나 결정 기록 갱신을 살핀다. 사용자는 왜 그 작업에 테스트나 명세가 필요했는지 생각해 볼 수 있다. 절차의 목적은 기록된 설명이 있는 범위에서 확인하며, 성공과 절차의 인과는 별도로 검토해야 한다. |
| **에이전트 시스템 이해하기** | 하위 에이전트가 자료를 조사한 사례에서 전달된 지시, 하위 에이전트의 반환, 상위 에이전트의 후속 모델 요청을 확인한다. 반환에 담긴 자료가 모델 입력에 포함됐더라도, 초안의 특정 수치에 어떻게 쓰였는지는 해당 산출물과 출처에서 따로 확인한다. |

## 5. 기술 스택과 안전한 처리

첫 버전은 **Electron, React, TypeScript**를 사용한다. 개발과 빌드는 `electron-vite`를 사용하고, 화면 상태와 스타일은 React 기본 상태와 CSS로 관리한다.

- **Main**은 파일·폴더 선택, 경로와 식별자 검증, 번들 탐색, reducer 실행을 맡는다. `rollout`과 `state.json`을 규칙으로 파싱해 표시 항목과 근거 위치를 구성한다. 등록 경로와 파싱 결과는 메모리에 두며, 변환 출력은 앱이 관리하는 임시 파일에만 쓰고 사용 후 정리한다. 원본 세션·번들은 읽기 전용으로 취급한다.
- **Preload**는 열기·갱신·탐색·근거 조회 등 필요한 동작만 제한된 IPC로 제공한다. Main에서 등록 소스, 인수와 실제 파일 위치를 검증한다. 번들 내부 참조는 해당 번들 경계 안에서만 해석하며, 기록에서 나온 경로를 임의의 파일 읽기나 실행에 사용하지 않는다.
- **Renderer**는 파싱한 데이터로 화면을 그린다. 행을 펼치고 선택할 때는 받은 데이터를 쓰고, 추가 근거가 필요하면 등록 소스의 참조를 조회한다. 로그의 명령어, 코드, 메시지, 링크, 파일 경로는 데이터로 표시하며 자동 실행·탐색하지 않는다. 로그를 HTML로 실행하지 않도록 하고 파일·프로세스 권한은 Renderer에 노출하지 않는다.

reducer는 검증한 Codex 실행 파일을 셸 없이 인수 배열로 호출한다. 입력이 손상됐거나 크기·처리 시간 때문에 완료하기 어려운 경우 읽기 또는 변환 실패로 표시하고, 성공한 이전 스냅샷의 근거를 보존한다. 로컬 로그가 담고 있는 지침, 소스, 자격 증명 등 민감한 내용은 외부로 전송하지 않으며 앱 자체 진단 로그에 원문을 복제하지 않는다.

## 6. 구현 완료 기준

| 조건 | 기대 결과 |
| --- | --- |
| 같은 채팅의 세션 파일과 첫 번들을 열거나, 번들의 소속이 불일치·미확인임 | 일치하면 세션과 번들을 각각 볼 수 있다. 불일치·미확인 번들의 연결을 보류하고 문제가 있는 소스를 표시한다. 상세 번들이 없어도 유효한 세션 기록을 볼 수 있다. |
| 같은 채팅의 새 번들과 다른 채팅의 번들을 탐색하거나, 기존 번들을 다시 직접 추가함 | 탐색은 등록되지 않은 동일 채팅 번들만 제안하며 직접 추가에도 같은 식별 규칙을 적용한다. `trace_id`가 같은 번들은 중복 등록되지 않는다. |
| 같은 채팅에 되돌리기 전후의 rollout이 있고, 두 흐름에 대응하는 상세 번들이 있음 | 선택한 파일에 연결된 이전 구간까지만 대화에 표시한다. 원본의 되돌린 턴은 원본 rollout에서 볼 수 있다. 턴 ID가 일치하는 번들로 이동하고 대화에서 읽던 위치로 돌아갈 수 있다. |
| 현재 번들과 세션 파일에 기록이 추가되어 갱신함 | 등록 경로의 추가 기록과 확인 시점을 반영한다. 번들 선택과 안정적으로 대응하는 행동의 선택·읽던 위치를 유지한다. |
| 성공한 작업을 열어 질문 입력 없이 탐색함 | 턴을 펼쳐 행동과 주체를 구별하고, 앞뒤 맥락과 확인된 관계를 따라 개별 입력·결과와 근거를 본 뒤 읽던 자리로 돌아올 수 있다. |
| 같은 스냅샷을 다시 파싱하거나 같은 이름의 호출이 여러 번 겹침 | 같은 뷰어 버전에서 순서·이름·묶음·근거 연결이 동일하다. 기록에 근거해 서로 다른 호출과 주체를 구별한다. |
| 호출 완료·종료 코드 `1`이 함께 있거나 도구 반환의 후속 모델 요청 포함 여부가 다름 | 호출 종료와 종료 코드가 각각 보인다. 실제 요청에 들어간 근거가 있는 경우에만 포함 관계를 표시한다. |
| 근거 본문이 있거나, 종료 이벤트·원시 근거가 없거나 페이로드가 잘림 | 확인된 범위와 마지막 기록 시점, 근거 유형과 접근 가능 여부를 표시한다. 열 수 있는 원시 레코드나 본문으로 이동할 수 있고, 참조만 있으면 확인 가능한 파생 필드와 원시 위치·ID를 볼 수 있다. |
| 실행 파일을 확인할 수 없거나 적합하지 않음, 경로가 이동함, 재읽기·변환이 실패함 | 실패 이유와 대상을 표시한다. 이전 결과가 있으면 해당 소스의 이전 확인 시점과 함께 보존한다. 원본은 변경하지 않는다. |
| 기록에 명령어, HTML, URL 또는 번들 밖을 가리키는 참조가 포함됨 | 내용을 데이터로 표시한다. 기록에 따라 코드 실행, 외부 탐색, 등록 범위 밖 파일 읽기, 네트워크 전송이 발생하지 않는다. |

## 7. 사용성 평가와 제품 가설

로그 경험이 다른 사용자 3~5명부터 탐색적으로 평가한다. 참여자마다 평면 기록 또는 리더 중 먼저 볼 형식을 배정한다. 그 형식에서 성공 사례를 자유롭게 둘러본 뒤 지정 조사 과제를 수행한다. 새 사례에서의 판단을 확인한 다음, 두 번째 형식에서 비슷한 난도의 지정 조사 과제를 수행한다. 형식마다 같은 범위의 기록을 제공하고 사례와 형식의 순서를 참여자별로 교차 배정한다. 상세 기록 확보, 적합한 실행 파일 지정, 변환에서 생기는 마찰도 따로 기록한다.

| 평가 대상 | 관찰 방법 |
| --- | --- |
| **사용성** | 지정 조사에서 근거를 찾았는지, 시간과 동선은 어떠했는지, 주체·입력·결과·확인 가능한 관계를 정확히 읽었는지 기록한다. 일부 기록만 제공된 사례에서 결론의 범위를 과장하는지도 본다. |
| **자발적 탐색** | 힌트를 주기 전에 어떤 행동이 관심을 끌었는지, 낯선 도구나 개념을 발견했는지, 스스로 어떤 질문을 만들고 어떤 기록을 더 열었는지 관찰한다. |
| **이해의 형성** | 본 것을 자신의 말로 설명하게 한다. 기록된 사실과 가설을 구분하는지, 행동 간 관계와 성공 사례의 절차가 해결하려던 문제를 어떤 근거로 설명하는지, 이전 가정에 변화가 있었다면 계기가 무엇인지 살핀다. |
| **학습 전이** | 첫 형식을 사용한 뒤 다른 형식이나 해설을 접하기 전에, 도구나 맥락이 다른 새 사례를 공통 형식으로 제공해 근거 판단과 위임·검증 선택을 살핀다. 반복 사용 뒤에는 실제 후속 작업의 프롬프트, 위임 범위, 개입 판단에 변화가 있었는지 사례 단위로 확인한다. |

작업 시간과 열어 본 항목 수는 관찰 행동의 지표다. 이해와 전이는 사용자의 설명, 제시한 근거, 다른 작업에서의 적용으로 살핀다. 질문 수나 특정 결론 도달을 성공 조건으로 삼지 않는다. 소규모 평가는 관찰 가능한 개선점과 가설을 찾는 데 쓰며, 방법론 학습이나 장기 전이의 효과를 확정하는 근거로 삼지 않는다.

## 8. 착수 시 확인할 사항

- 기존 검증에서는 이 PC에서 같은 채팅에 속한 번들 두 개와 진행 중인 스키마 3 번들의 reducer 변환을 확인했다. 지원할 Windows 데스크톱 설치본에서 기록 사전 활성화, 소스 위치, 기록에 사용한 실행 파일을 구하는 경로, 임시 출력 옵션을 다시 확인한다.
- 성공·부분 기록 사례를 열어 하위 에이전트, 도구 결과, 모델 요청, 원본 위치가 실제 필드로 어디까지 이어지는지 확인한다. 기록마다 놓친 정보와 화면의 표시 한계를 문서화한다. 평가용으로 공유할 기록이 필요하면 같은 구조의 별도 예시를 준비한다.
