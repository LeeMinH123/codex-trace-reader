# 제품 철학 · 에이전트 작업을 관찰하며 위임을 배우기

**AI 에이전트가 대부분의 소프트웨어 개발을 수행하는 상황에서, 사람이 여전히 위임하고 개입하는 주체라면 무엇을 이해해야 하는가?**

모델의 코드 생산성이 높아지고 하네스, 스킬, 개발 도구와 방법론이 빠르게 바뀌는 환경을 상정한다. 사람은 코드를 직접 읽거나 작성하는 일을 크게 줄이고, 구현과 함께 명세·테스트·설계 문서·결정 기록의 작성과 관리도 맡길 수 있다. 그 상황에서 사람이 목표와 수용 기준을 정하고, 프롬프트와 피드백을 주며, 중요한 선택을 내린다면 **소프트웨어 개발과 에이전트의 작동 원리에 관한 정신모형이 더 적절한 위임과 개입에 도움이 된다**는 것이 제품의 핵심 가설이다. 사람의 감독 필요성과 판단의 적합성은 작업, 위험, 가용한 근거에 따라 달라진다.

## 1. 스스로 질문하는 사용자

사용자는 실행 기록에서 사소한 행동 하나를 보고도 스스로 질문을 만들고, 다른 자료를 찾아보고, 기존 이해를 고칠 수 있다. 예를 들어 에이전트가 실행한 `rg "authentication" src/`를 처음 본 사람은 `rg`가 어떤 도구인지부터 궁금해할 수 있다. 이어서 검색어가 어떻게 해석되는지, `src/` 바깥에는 어떤 정보가 있는지, 결과가 없을 때 어디까지 결론을 내릴 수 있는지 조사할 수 있다. 명령어 하나에서 출발해 파일 시스템, 검색 범위, 불완전한 정보로 결론을 내리는 문제까지 이해가 이어질 수 있다.

관찰한 정보는 이미 가진 질문에 답하기도 하고, 이전에는 떠올리지 못한 질문과 사고의 틀을 만들기도 한다. 사용자는 호기심이 생긴 행동을 따라가거나, 구경을 마치거나, 바깥에서 더 조사할 수 있다. 제품은 질문 입력, 정해진 탐색 순서, 발견한 문제에 대한 조치 없이도 쓸 수 있어야 한다.

## 2. 정신모형과 위임

사람이 목표와 지시를 부여하는 환경에서 **그 사람의 정신모형은 에이전트 시스템의 상위 제어 요소 중 하나**다. 목표 설정, 피드백, 검증 요청, 개입 시점에 실제로 영향을 주기 때문이다. 정신모형에는 서로 다른 판단에 쓰이는 이해가 포함된다.

| 이해의 대상 | 판단에 쓰이는 예 |
| --- | --- |
| 소프트웨어 개발과 문제 해결 | 명세, 수용 기준, 테스트, 설계 기록이 각각 어떤 문제를 해결하고 어떤 조건에서 비용을 감수할 만한지 판단한다. |
| 에이전트 시스템 | 모델의 능력과 한계, 하네스와 스킬, 도구 호출, 컨텍스트 구성과 지시 체계가 어떤 행동과 정보 접근을 가능하게 하는지 살핀다. |
| 위임과 개입 | 목표와 제약, 허용할 실패의 영향, 확인이 필요한 예외를 정하고, 그 범위 안에서 구현·탐색·검증을 얼마나 맡길지 결정한다. |

예를 들어 좁은 검색 범위를 관찰했다면 먼저 그 검색의 목적과 뒤이어 한 확인을 살펴볼 수 있다. 중요한 누락이 있었다면 현재 작업을 수정하거나 다음 프롬프트에서 필요한 범위를 명시할 수 있다. 같은 문제가 반복되면 스킬이나 하네스의 변경 또는 불필요한 지시의 제거를 검토할 수 있다. 기존 범위가 적절했다면 그대로 둘 수도 있다. 사람의 모형에도 오류와 빈틈이 있으므로, 영향이 크거나 되돌리기 어려운 결정에는 승인된 기준, 실제 실행 결과, 독립적인 검증을 함께 활용한다.

## 3. 실행 기록을 보는 네 가지 이유

| 관찰 방식 | 살펴볼 수 있는 것 |
| --- | --- |
| 사후 조사 | 완료 보고에 나온 테스트가 어떤 명령·대상·환경에서 실행됐는지, 어떤 결과가 남았는지, 특정 자료나 도구 결과가 다음 모델 요청에 포함됐는지 확인한다. |
| 탐색적 관찰 | 가설 없이 타임라인을 훑다가 낯선 명령, 예상 밖의 탐색 순서, 우회 작업을 발견한다. 그중 관심이 생긴 행동에서 자기 질문을 시작한다. |
| 성공한 개발 과정 관찰 | 요구사항과 제약 파악, 코드 탐색, 수용 기준과 설계 대안 검토, 테스트·구현, 실패 후 수정, 검증·리팩터링, 문서 갱신, 하위 에이전트의 분담과 통합을 흐름 속에서 살핀다. |
| 에이전트 시스템 관찰 | 어떤 지침과 대화 항목이 어느 모델 요청에 포함됐는지, 하위 에이전트에 어떤 작업이 전달됐는지, 도구의 반환과 실제 모델 입력이 어디서 달라지는지 확인한다. |

성공한 과정에서도 방법론을 적용한 조건을 질문할 수 있다. 테스트 주도 개발(TDD)에서는 먼저 작성한 테스트가 어떤 기대 동작을 고정했는지, 명세 주도 개발(SDD)에서는 어느 정도의 명세가 작업 조율과 수용 판단에 필요했는지 볼 수 있다. 아키텍처 결정 기록(ADR)은 어떤 선택의 이유를 다시 알아야 할 때 유용한지, 지속적 통합(CI)은 어느 환경에서 어떤 검증을 반복 가능하게 했는지 살필 수 있다. 사례에 드러난 제약과 절차는 적용 조건을 생각해 볼 자료다. 특정 절차가 성공을 일으켰는지는 대안이나 별도의 증거가 필요한 질문이다. [Michael Nygard, *Documenting Architecture Decisions*](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## 4. 경험을 압축하고 다른 작업에 적용하기

기술이 바뀌면 지식의 쓰임도 달라진다. 사용자는 기록의 세부를 다시 찾아볼 수 있는 상태에서 자신에게 필요한 이해를 남긴다.

| 지식의 층위 | 검색 사례 |
| --- | --- |
| 개별 사실 | 당시 명령어, 인수, 경로, 종료 코드와 출력 |
| 작동 원리 | 검색 범위와 제외 규칙, 도구 호출과 반환, 후속 요청에 결과가 포함되는 조건 |
| 상위 원리 | 제한된 정보로 탐색하기, 불확실성에 맞춰 추가 검증하기, 피드백에 따라 위임 범위 조정하기 |

정확한 명령어가 당장 필요할 수도 있고, 범위와 근거를 함께 보는 습관이 새로운 도구를 배우는 데 쓰일 수도 있다. 외부 기록과 문서는 세부를 보존하고, 사용자는 경험을 연결해 자신의 이해를 압축한다. **학습 전이**는 예를 들어 다른 검색 도구나 하네스가 쓰인 작업에서도 사용자가 관찰 범위를 확인하고, 빈 결과의 의미를 조건에 맞게 설명하고, 추가 검증의 필요성을 판단하는 데서 살핀다. 같은 화면에서 빨리 찾는 능력과 지속적인 전이는 별도의 평가 대상이다. 전이 가능성은 검증할 가설이다. [Bransford와 Schwartz, *Rethinking Transfer*](https://doi.org/10.3102/0091732X024001061)

### 인지부채의 두 측면

Storey는 팀의 공유 이해가 약해지는 문제를 인지부채로, 명시된 목표와 제약·결정 근거가 사라지는 문제를 의도부채로 설명한다. 이 제품은 개인의 위임 판단에 그 관점을 적용해 두 가지 비용을 살핀다. [Storey, *From Technical Debt to Cognitive and Intent Debt*](https://arxiv.org/abs/2603.22106)

- 필요한 이해가 부족하면 새 상황을 파악하거나 이전 결정의 근거를 복원하는 데 시간이 걸리고, 확인해야 할 예외를 놓치거나 작업을 되풀이할 수 있다.
- 일시적인 구현 세부를 모두 기억하거나, 한 번의 예외마다 공통 지시와 관리 규칙을 추가하면 이후 작업에서 읽고 대조하고 갱신할 비용이 커진다.

제품은 세부를 다시 볼 수 있게 하여 기억의 부담을 낮춘다. 승인한 기준과 중요한 결정 이유는 기존 명세·이슈·PR·ADR의 적절한 위치에 남길 수 있다. 승인이나 이유가 기록된 적이 없다면 실행 흔적만으로 복원하기 어렵다. 어떤 세부가 나중에 유용할지는 사용자의 작업과 관심에 따라 달라지므로, 화면에서 접어 둔 정보에도 접근 경로를 제공한다.

## 5. 정보를 구조화하는 이유와 해석의 한계

**정보이론**에서 정보량은 정의한 가능성과 확률에서의 불확실성에 관한 개념이다. 로그 길이나 이벤트 수로 사람에게 의미 있는 정보의 양을 알 수는 없다. 제품에서 압축은 반복되는 항목을 묶고 순서와 관계를 드러내 탐색 비용을 줄이는 화면 설계다. 현재 알려진 질문만을 기준으로 원본을 걸러내면 새 질문에 필요한 단서가 사라질 수 있다. 개요를 간결하게 만들되 개별 행동과 원본 근거로 내려갈 길을 둔다. [Shannon, *A Mathematical Theory of Communication*](https://people.math.harvard.edu/~ctm/home/text/others/shannon/entropy/entropy.pdf) · [Shneiderman, *The Eyes Have It*](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf)

**의사결정이론**의 관점에서 추가 관찰의 가치는 가능한 선택과 결과, 관찰에 드는 비용에 따라 달라진다. 현재 작업의 수정, 후속 프롬프트 개선, 공통 스킬이나 하네스 변경 검토, 추가 조사, 현 상태 유지가 모두 가능한 선택이다. 판단의 중요도와 실패 위험이 크면 독립 근거를 찾는 비용을 감수할 수 있고, 당장 선택이 바뀌지 않아도 관찰 경험이 이후 학습에 도움이 될 수 있다. 이 개념들은 설계와 평가를 위한 관점이며, 학습과 호기심의 가치를 하나의 수치로 환산할 수 있다고 가정하지 않는다. [Howard, *Information Value Theory*](https://doi.org/10.1109/TSSC.1966.300074)

**기록의 권위는 질문에 따라 달라진다.** 승인한 요청과 명세 버전은 당시 기대를, Git과 PR은 특정 리비전의 변경을, CI와 실제 실행은 해당 빌드·환경·입력에서의 결과를 보여준다. 트레이스는 기록된 요청, 도구 호출과 반환, 메시지 전달, 에이전트가 보고한 내용을 보여준다. 예를 들어 필수 입력을 선택 입력으로 바꾸면서 명세와 테스트도 함께 수정하면 세 산출물이 일관되고 테스트가 통과할 수 있다. 변경된 기준의 승인 여부는 승인 기록에서, 실제 동작은 해당 결과물에서 확인한다. 호출과 반환이 잇따랐다는 사실만으로 반환값이 다음 모델 입력에 포함됐는지, 선택에 영향을 줬는지 알 수 없다. 모델의 비공개 내부 추론은 관찰 범위 밖이다. [Codex Rollout Trace](https://github.com/openai/codex/blob/main/codex-rs/rollout-trace/README.md)

**의미 판단과 무한후퇴**는 분석을 더하는 것만으로 해결되지 않는다. 모델, 하네스, 도구, 스킬, 여러 실행 주체가 얽힌 작업에서는 동일한 관찰에도 여러 설명이 가능하다. AI 분석자도 무엇을 중요하게 보고 어떤 가설을 검토할지, 언제 조사를 끝낼지 결정한다. 그 분석의 정당성을 다시 같은 종류의 분석으로 확인하는 과정을 반복하면 판단 근거가 늘지 않을 수 있다. 새 실행, 독립적인 기준, 다른 관점에서의 반례 검토처럼 추가 정보가 생기는 확인은 유용하다. 사용자에게는 판단의 영향과 남은 불확실성에 맞춰 조사를 끝내거나 이어갈 선택권이 있다. 필요할 때 AI는 검색, 설명, 근거 연결, 반례 검토를 도울 수 있다. 기본 화면에서는 사람이 원래 기록을 따라가며 직접 의미를 형성한다.

## 6. 제품 설계 원칙

**트레이스 리더는 에이전트의 복잡한 실행 기록을 충실하게 구조화하고 직관적으로 시각화하여, 사용자가 자유롭게 관찰·탐색·조사하고 자신의 정신모형을 형성하고 갱신하도록 돕는다.**

| 원칙 | 화면에서의 적용 |
| --- | --- |
| 구조화 | 확보한 기록에서 순서, 실행 주체, 입력, 결과와 확인된 연결을 재구성한다. |
| 시각화 | 전체 흐름을 훑으면서 행동과 주체를 구별하고, 관심 항목의 앞뒤 맥락을 찾을 수 있게 한다. |
| 점진적 공개 | 전체 흐름에서 개별 행동으로, 이어서 표시를 뒷받침하는 기록 근거로 들어갈 수 있게 한다. |
| 접근의 개방성 | 접힌 정보도 사용자가 펼치거나 원본 위치로 따라갈 수 있게 한다. 누락, 잘림, 참조만 남은 경우에는 접근 가능한 범위를 보여준다. |
| 관찰과 해석의 구분 | 기록에 있는 사실, 뷰어가 규칙으로 만든 이름·묶음·관계, 해석과 확인할 수 없는 사항을 구별한다. 규칙 기반 표현에서도 해당 표시가 나온 필드와 적용한 규칙을 확인할 수 있게 한다. |
| 탐색 자율성 | 질문, 오류, 완료 보고 어느 것도 진입 조건으로 삼지 않는다. 관찰의 시작점과 깊이는 사용자가 고른다. |

첫 버전은 Windows에서 이미 확보한 로컬 Codex 기록 한 채팅을 읽는 뷰어로 이 원칙을 검증한다. 즉시 확인할 가설은 사용자가 평면 기록보다 실행의 순서와 관계를 쉽게 읽으면서 근거의 한계를 더 잘 또는 적어도 같은 수준으로 구별할 수 있다는 것이다. 질문 형성, 이해의 변화, 다른 작업으로의 전이는 별도로 관찰한다. 상세 기록 확보의 마찰과 지원 번들의 정보 범위도 제품 가치에 영향을 준다. [제품 요구사항](prd.md)
